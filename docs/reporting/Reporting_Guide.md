# Reporting Guide

This repo produces four kinds of reports across the patch lifecycle. They are
separate systems that share an output convention (per-run JSON plus a rendered
HTML, written to the control node and, where applicable, the target host).

For the fast command reference see [Reporting_QuickRef.md](Reporting_QuickRef.md).
Control-node report paths derive from `$CHOCO_FLEET_DATA_ROOT`; `/opt/ansible` is
the production default used here.

## Overview

| Report | Stage | Engine | Output |
| Pre-patch readiness | before patching | [playbooks/patchReady.yml](../../playbooks/patchReady.yml) | HTML on control node |
| Post-patch report | during/after chocoDeploy | [playbooks/roles/chocoDeploy/tasks/ops/report.yml](../../playbooks/roles/chocoDeploy/tasks/ops/report.yml) | per-run JSON + daily HTML |
| Fleet summary | after a window | [playbooks/roles/chocoDeploy/files/fleet_summary.py](../../playbooks/roles/chocoDeploy/files/fleet_summary.py) | HTML, optional txt + json |
| Software usage | anytime (read-only) | [playbooks/softwareUsage.yml](../../playbooks/softwareUsage.yml) | per-host + fleet HTML |
| Live compliance evidence | after a change or interruption | [playbooks/tools/collect_compliance_state.yml](../../playbooks/tools/collect_compliance_state.yml) + [playbooks/tools/build_compliance_evidence.py](../../playbooks/tools/build_compliance_evidence.py) | fleet HTML from live version checks |

## Report selection gate

Choose the report engine from the lifecycle stage. Do not hand-author a replacement
report when one of these engines applies.

| Need | Use | Output location | Coverage rule |
| Before a change window | `playbooks/patchReady.yml` | `/opt/ansible/LOGS/patchReady/` | The HTML covers the inventory passed to patchReady. |
| Rebuild target daily HTML from existing target JSON | `chocoDeploy` with `-e "deployment=report_only"` | `C:\tools\chocolog\<date>_chocoDeploy.html` | This rebuilds target-side HTML; it does not create missing control-node JSON. |
| Final control-node fleet roll-up | `playbooks/roles/chocoDeploy/files/fleet_summary.py` | `<output-dir>/<UTC>_chocoDeploy_fleet_summary.html` | The script's `Found N JSON files across M hosts` line is the evidence coverage. |

Before presenting a fleet summary as final, compare `M` with the intended host
scope. If it is lower, keep the generated HTML as a partial evidence roll-up and
state the missing coverage. Never fill the gap with manually invented HTML or
Markdown. The fleet-summary HTML is generated by `fleet_summary.py`; its optional
JSON and text files belong under the `detailed/` subdirectory.

### Interrupted-run recovery

If the controller is interrupted before the normal end-of-run report task, collect
the target-side JSONs that survived on each host before running the fleet summary:

```bash
ansible-playbook playbooks/tools/collect_chocoDeploy_reports.yml \
  -i <inventory> \
  --vault-password-file=vault/.vault_key.txt \
  -e @vault/corp-ans-secret.yml \
  -l basic_hosts \
  -e "choco_report_collect_dir=/opt/ansible/LOGS/chocoDeploy/recovered"
```

The collector is read-only against targets and fetches all target-side JSON files;
it does not filter by filesystem age. `fleet_summary.py` then applies the official
`--last-hours`, `--since`, or `--until` timestamp window. It reads normal
`<UTC>_<host>_chocoDeploy.json` files at the top level of `--json-dir` and the
collector's `<host>/<UTC>_chocoDeploy.json` files one folder down; any other
subfolder (evidence copies, compliance output, `reports/`, `archive/`) is ignored,
so point `--json-dir` at the folder you mean to summarize.

### Live compliance evidence

When the operational run was interrupted before per-run JSON reporting, use the
read-only compliance evidence path instead of inferring state from task output:

1. Run `playbooks/tools/collect_compliance_state.yml` against the campaign inventory.
2. Run `playbooks/tools/build_compliance_evidence.py` with the campaign CSVs and
  `playbooks/roles/chocoDeploy/defaults/main.yml`.
3. Run `fleet_summary.py --json-dir /opt/ansible/LOGS/chocoDeploy/compliance-json`.

The evidence checks Chocolatey package versions, uninstall-registry versions,
installed .NET runtime tracks, .NET Framework release state, pending reboot
advisories, and unreachable hosts. The resulting fleet HTML is a compliance
evidence report; it is not a deployment report and does not modify software.

## 1. Pre-patch readiness (patchReady)

### What it checks
No software changes, no reboots (one housekeeping side effect, below). Per host:
- WinRM connectivity (with DNS vs auth vs timeout failure classification)
- Pending-reboot indicators: CBS RebootPending, WU RebootRequired,
  SessionMgr PendingFileRenameOperations, ComputerName rename pending
- C: free space against `patch_ready_disk_threshold_gb` (default 5 GB)
- Chocolatey presence and version sanity
- Uptime (days)

### Scoring
- READY: WinRM ok, no actionable reboot, disk above threshold, choco ok
- WARN (printed as WARN in the console, shown as CHECK in the HTML): an
  actionable reboot, low disk, or missing/bad choco
- FAIL: WinRM unreachable

Actionable reboot reasons in patchReady are CBS `RebootPending`, WU
`RebootRequired`, and a pending computer rename. `PendingFileRenameOperations` is
reported but does not gate. Note that chocoDeploy classifies WU `RebootRequired`
as soft (informational), so the two tools can disagree about the same host.

### How it is built
The play gathers checks via an inline PowerShell block, computes `_pr_status`
and `_pr_host_result` per host, then renders one HTML file with
[playbooks/templates/patchReady.html.j2](../../playbooks/templates/patchReady.html.j2).
The template groups hosts into a collapsible Problem section (open by default)
above a collapsible Ready section (collapsed by default), with summary cards and
a Reboot Flags legend at the top.

### Output
`/opt/ansible/LOGS/patchReady/<UTC>_<inventory>_patchReady.html`
(directory `patch_ready_output_dir`).

### Side effect
On reachable hosts it also archives chocoDeploy logs older than
`patch_ready_log_cleanup_days` (default mirrors `choco_deploy_local_report_retain_days`,
90) into `C:\tools\chocolog\archive\`.

## 2. Post-patch report (chocoDeploy)

Produced by every chocoDeploy run via [playbooks/roles/chocoDeploy/tasks/ops/report.yml](../../playbooks/roles/chocoDeploy/tasks/ops/report.yml).

### Structure
Each run builds a `choco_deploy_report_events` list (NoChange / Installed /
Upgraded / Converted / Removed entries) plus a summary object
(installed, upgraded, converted, removed, compliant, errors) and an advisories
block (for example soft pending-reboot reasons).

### Outputs
- Per-run JSON on the target: `C:\tools\chocolog\<UTC>_..._chocoDeploy.json`
- Per-run JSON on the control node: `/opt/ansible/LOGS/chocoDeploy/`
- Consolidated daily HTML on the target: `C:\tools\chocolog\<date>_chocoDeploy.html`,
  rendered by [playbooks/roles/chocoDeploy/templates/report.html.j2](../../playbooks/roles/chocoDeploy/templates/report.html.j2),
  combining all runs from that UTC date and embedding a JSON block for downstream parsing.

### Rebuild without changing software
`-e "deployment=report_only"` re-renders the HTML from existing JSONs only.

### Retention
Target per-host logs older than `choco_deploy_local_report_retain_days` (default 90)
are compressed into `C:\tools\chocolog\archive\`.

### Reporting caveat (pwsh)
A PowerShell upgrade can disconnect WinRM mid-task (HTTP 400). The install still
completes and is verified, and the report records the Converted/Installed event
off either a normal change result or that transport failure, so pwsh conversions
are not undercounted. See the chocoDeploy Guide for the underlying mechanics.

## 3. Fleet summary roll-up

[playbooks/roles/chocoDeploy/files/fleet_summary.py](../../playbooks/roles/chocoDeploy/files/fleet_summary.py)
reads the control-node per-host JSONs and writes one fleet HTML summary for a
downtime review board to `/opt/ansible/LOGS/chocoDeploy/reports/` (`--output-dir`).
`--include-text` and `--include-json` add .txt and .json copies under `detailed/`.

Key behavior:
- Groups hosts by site derived from each JSON's inventory source
- Last-run-wins dedup: when a host ran multiple times, only the latest event per
  software is counted, so retries replace earlier failures
- Retry annotation: hosts that needed multiple runs show retry counts

Run on ansible-ctl-01 after a window, then pull output to a local workstation. Window selection flags:
`--today`, `--last-hours N`, or `--since/--until <UTC>`; input `--json-dir <dir>`;
presentation `--short-names`; output `--output-dir <dir>`, `--include-text`,
`--include-json`; housekeeping `--archive`, `--retain-days N`.

`--archive` moves the consumed per-host JSONs into
`<json-dir>/archive/<UTC>_chocoDeploy_run.zip` (they leave the JSON directory, so a
later summary of the same window will not find them) and deletes archive zips older
than `--retain-days` (default 90). Leave it off when the JSONs are still needed as
evidence.

## 4. Software usage scan (softwareUsage)

[playbooks/softwareUsage.yml](../../playbooks/softwareUsage.yml) is a read-only role
that reads Security EventID 4688 (process creation) on each target and reports which
catalog applications were actually used in a lookback window. No software changes,
no reboots.

Per-app verdicts: used_recently / unused_in_window / audit_off.

Tunables:
- `usage_days` (default 30) - lookback window
- `usage_min_executions` (default 2) - how many runs count as "used"; set 1 for "used at all"

After a run, build the fleet HTML roll-up with the role's own summary tool:
`python3.12 playbooks/roles/softwareUsage/files/fleet_summary.py --last-hours 24`.

## Output locations summary

| What | Where |
| patchReady HTML | `/opt/ansible/LOGS/patchReady/` (control) |
| chocoDeploy per-run JSON | `/opt/ansible/LOGS/chocoDeploy/` (control), `C:\tools\chocolog\` (target) |
| chocoDeploy daily HTML | `C:\tools\chocolog\<date>_chocoDeploy.html` (target) |
| fleet summary | `/opt/ansible/LOGS/chocoDeploy/reports/` (control) |
| softwareUsage per-host HTML + JSON | `/opt/ansible/LOGS/softwareUsage/` (control), `C:\tools\usagelog\` (target) |
| log archives | `C:\tools\chocolog\archive\` (target) |

All control-node logs live under `/opt/ansible/LOGS/`, which is outside
the repo and never synced to DevOps.
