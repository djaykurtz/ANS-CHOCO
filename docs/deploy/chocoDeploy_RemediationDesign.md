# chocoDeploy Remediation Inventory Auto-Generation

**Design Document for In-Fleet Software Recovery**

**Status:** Proposed design, not implemented in the current fleet-summary tool.  
**Example context:** Vendor removal can precede a failed replacement install (for example, rc=1603 with CBS:RebootPending).  
**Solution:** Enhance fleet_summary.py to auto-generate remediation inventories, then extend choco_conversion to handle targeted fresh installs.

---

## Problem Statement

**Scenario:** During a `choco_conversion` fleet run:
1. Host X has vendor Docker installed
2. Vendor Docker is removed (prepping for choco conversion)
3. Choco Docker install fails (rc=1603 due to CBS:RebootPending)
4. Host X is left with **no Docker at all**
5. On reboot and retry, `choco_conversion` doesn't help — no vendor to convert, no choco to upgrade

**Current workaround:** Manually create inv-remediation.yml, run `choco_baseline` with targetSoftware filter (violates baseline safety boundary).

**Better solution:** Auto-detect failures → auto-generate remediation inventory → re-run with smart `remediate_failed_hosts` gate in `choco_conversion` (stays idempotent, no new mode).

---

## Design: Three-Phase Flow

### Phase 1: fleet_summary.py Analysis & Inventory Generation

**After fleet run completes, fleet_summary.py analyzes JSON reports:**

```python
def extract_remediation_targets(agg, json_files):
    """
    Scan all per-host reports for unresolved software failures.
    Return dict of {software_name: [failed_hosts]}
    """
    remediation_targets = defaultdict(list)
    
    for host_data in agg["hosts"].values():
        # Look for hosts with actual software install/convert failures
        # (not pending-reboot advisories)
        for err in host_data["error_details"]:
            # error_details contains [software_label, ...]
            # only from non-advisory errors
            if host_data["status"] == "Failed":
                remediation_targets[err].append(host_data["hostname"])
    
    return dict(remediation_targets)
```

**Output: Remediation inventories** (generated in `reports/` subdir):
Control-node paths derive from `$CHOCO_FLEET_DATA_ROOT`; `/opt/ansible` is the
production default used here.

```
/opt/ansible/LOGS/chocoDeploy/reports/remediation/
├── 20260617T035253Z_remediation_docker-desktop.yml       # 4 hosts
├── 20260617T035253Z_remediation_powershell-core.yml      # 1 host
├── 20260617T035253Z_remediation_all-failed.yml           # 5 hosts combined
└── README.txt                                            # Instructions
```

### Phase 2: choco_conversion Mode Enhancement

**Add a new control variable `remediate_failed_hosts`** (default: false):

```yaml
# In playbooks/chocoDeploy.yml
- name: chocoDeploy | Parse remediation inventory (optional)
  ansible.builtin.set_fact:
    remediation_software: "{{ hostvars[inventory_hostname].get('remediation_software', '') }}"
    remediate_failed_hosts: "{{ remediate_failed_hosts | default(false) | bool }}"
  tags: always
```

**Modify install-one task** to accept a bypass-conversion flag:

```yaml
# In playbooks/roles/chocoDeploy/tasks/ops/install-one.yml
# Existing task:
- name: Install-one | Convert vendor to Choco
  block:
    - name: Detect vendor install
      # ... existing vendor detection logic ...
      when: not remediate_failed_hosts or remediation_software != install_software

    - name: Remove vendor if detected
      # ... existing removal logic ...
      when: not remediate_failed_hosts or remediation_software != install_software

  # If remediate_failed_hosts=true AND remediation_software matches, skip entire block
  # and jump directly to install

- name: Install-one | Install from Chocolatey
  # ... existing choco install logic (unchanged) ...
  # This always runs (conversion or fresh install)
```

**The gate in logic:**

```python
# Pseudocode for task conditionals:

When remediate_failed_hosts=true AND host has remediation_software var:
  IF remediation_software == current_target_software:
    SKIP vendor detection & removal
    GO DIRECT TO: choco install (fresh, not conversion)
  ELSE:
    RUN normal choco_conversion workflow (vendor detect → remove → install)

When remediate_failed_hosts=false OR host lacks remediation_software var:
  RUN normal choco_conversion workflow on all software
```

**Report events distinguish the mode:**

```json
{
  "software": "docker-desktop",
  "action": "Installed",
  "notes": "Fresh install (remediation mode, vendor removal skipped)",
  "remediation_run": true
}
```

vs normal conversion:

```json
{
  "software": "docker-desktop",
  "action": "Converted",
  "notes": "Vendor MSI → Chocolatey"
}
```

### Phase 3: Execution & Idempotency

**First run (260616 main):**
```bash
ansible-playbook playbooks/chocoDeploy.yml \
  -i inventory/Deployment/260616/inv-260616-main.yml \
  -e "deployment=choco_conversion"
  # Result: 118 succeeded, 5 failed (docker install blocked by CBS)
```

**Post-run analysis (auto-executed by fleet_summary.py or manual):**
```bash
python3.12 playbooks/roles/chocoDeploy/files/fleet_summary.py \
  --last-hours 6 --short-names --generate-remediation
  # Output: inv-remediation-docker-desktop.yml, inv-remediation-powershell-core.yml, README.txt
```

**Remediation run (second pass):**
```bash
# Step 1: Clear the CBS/reboot state
ansible-playbook playbooks/rebootHost.yml \
  -i /opt/ansible/LOGS/chocoDeploy/reports/remediation/20260617T035253Z_remediation_all-failed.yml \
  --vault-password-file=vault/.vault_key.txt \
  -l basic_hosts \
  -e "reboot_reason=Clear CBS before software remediation" \

# Step 2: Re-run choco_conversion with remediation gate
ansible-playbook playbooks/chocoDeploy.yml \
  -i /opt/ansible/LOGS/chocoDeploy/reports/remediation/20260617T035253Z_remediation_docker-desktop.yml \
  --vault-password-file=vault/.vault_key.txt \
  -l basic_hosts \
  -e "deployment=choco_conversion" \
  -e "remediate_failed_hosts=true"
  # Result: 4 hosts get fresh docker install (bypass vendor conversion)
```

**Idempotency check (third pass, same command):**
```bash
ansible-playbook playbooks/chocoDeploy.yml \
  -i /opt/ansible/LOGS/chocoDeploy/reports/remediation/20260617T035253Z_remediation_docker-desktop.yml \
  --vault-password-file=vault/.vault_key.txt \
  -l basic_hosts \
  -e "deployment=choco_conversion" \
  -e "remediate_failed_hosts=true"
  # Result: 4 hosts already have docker, install task is NoChange, report shows Compliant
```

✅ Idempotent: yes, running it again does nothing (target state reached)

## Safety Gates & Assumptions

1. **Requires explicit inventory generation:** User must run fleet_summary with `--generate-remediation` or manually create inventory. No auto-remediation without user action.

2. **Remediation inventory must have remediation_software var:** If missing, falls back to normal choco_conversion behavior (safe default).

3. **Reboot is recommended but not enforced:** README.txt documents reboot + re-run pattern. User can skip reboot if CBS isn't the blocker.

4. **One software per remediation run:** To keep it simple, generate one inventory per software (inv-remediation-docker-desktop.yml, not inv-remediation-mixed.yml). User can combine manually if needed.

5. **Fleet_summary marks remediation runs in report:** Easy to audit which runs used remediation mode vs normal conversion.

6. **remediate_failed_hosts=false is the default:** No surprises; existing scripts run unchanged.

## Migration Path (if implementing)

**Backward compatible:** Existing scripts don't use `remediate_failed_hosts`, so they run unchanged (normal choco_conversion). New remediation feature is opt-in.

**Future enhancement:** Could auto-trigger remediation after a threshold of failures (e.g., if >3 hosts fail same software, auto-generate inventory + suggest re-run). But start simple (manual trigger).

---

## Notes & Risks

1. **Fresh install vs conversion:** On remediation run, docker gets installed from choco directly (not converted from vendor). This is **intentional** — the vendor is already gone, and we just need the software back. Risk: if choco package differs from vendor, user may notice (unlikely, but possible).

2. **CBS:RebootPending isn't the only blocker:** Remediation assumes reboot clears the issue. If something else is wrong (disk full, network timeout, etc.), fresh install will also fail. Keep remediation README flexible ("if install still fails, check...").

3. **Versioning:** Remediation install uses the catalog floor version (same as normal install). If floor changed between runs, remediation host might install different version than originally-planned. Acceptable trade-off (floor is the source of truth).

4. **Multi-software failures:** Current design generates one inventory per software. If 4 hosts fail docker AND 3 hosts fail pwsh AND 1 host fails both, that's 3 separate inventories (or one combined inv-remediation-all-failed.yml). Keep it simple; generate per-software, user can combine manually.
